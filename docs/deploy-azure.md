Terraform for the service on Azure Container Apps, with Azure OpenAI as the
model and Application Insights receiving the OpenTelemetry stream. Everything
lives in [`terraform/azure/`](../terraform/azure). It is a second, independent
root module: the AWS stack in `terraform/` is untouched.

## What this builds

```
        your IP only (allowed_cidr)
                 │  :443, platform-managed TLS
                 ▼
   ┌────────────────────────────────────┐
   │ Container App (0..1 replica)       │
   │  ┌─────────┐   OTLP   ┌──────────┐ │        ┌──────────────────────┐
   │  │   api   │─────────▶│ collector│─┼───────▶│ Application Insights │
   │  └─────────┘ localhost└──────────┘ │        └──────────────────────┘
   └───┬────────────┬───────────────┬───┘
       │ token      │ token         │ TLS + password
       ▼            ▼               ▼
  Azure OpenAI   Key Vault     PostgreSQL Flexible Server
  (keys off)    (db-password)  (pgvector)

  All three arrows on the left use one user-assigned managed identity.
```

A separate Container Apps **job** runs `scripts/ingest.py` on demand.

## How it differs from the AWS stack, and why

| | AWS (`terraform/`) | Azure (`terraform/azure/`) |
|---|---|---|
| Compute | One EC2 instance running docker compose | Container Apps, scale to zero |
| Database | Postgres container on the same box | Managed PostgreSQL Flexible Server |
| Model | Groq, API key in SSM Parameter Store | Azure OpenAI, **no key**: managed identity |
| TLS | None (IP only) | Platform-managed on the default hostname |
| Telemetry | Not wired | OpenTelemetry to Application Insights |
| Cost floor | ~$0 on Free Tier | The database bills by the hour |

The AWS design optimises for a zero bill. This one optimises for showing the
managed-service shape of the same system, and pays for the database to do it.

## Secrets: what is and is not in Terraform state

The repo's rule is that no secret is ever stored in state. On Azure that takes
three different mechanisms, because three different things would otherwise
leak.

- **The model has no key.** `local_auth_enabled = false` disables API keys on
  the Azure OpenAI resource. The API presents a short-lived Microsoft Entra ID
  token from its managed identity instead
  ([`auth.py`](../src/evalgate_rag/auth.py)), and the identity holds only the
  inference role. There is nothing to store, rotate or leak.
- **The database password is ephemeral.** It is generated by an
  `ephemeral "random_password"` and handed to PostgreSQL and to Key Vault
  through write-only arguments (`administrator_password_wo`, `value_wo`).
  Terraform sends the value and does not record it; state holds only
  `db_password_version`. This needs Terraform 1.11 or newer.
- **The container app holds a reference.** Its `db-password` secret is a Key
  Vault secret URL resolved by the platform with the identity, not a value.

One value is in state deliberately: the Application Insights connection string.
It is an attribute of that resource, and it permits sending telemetry to it and
nothing else.

## Prerequisites

- An Azure subscription, and the Azure CLI signed in (`az login`).
- Terraform 1.11 or newer.
- Permission to create role assignments in the subscription (Owner, or
  Contributor plus User Access Administrator).
- Azure OpenAI quota for the chosen model in the chosen region. Check before
  applying, because model versions are retired on a schedule and the default in
  `variables.tf` will go stale:
  `az cognitiveservices model list -l swedencentral -o table`
- The GHCR image public, and built from a commit that includes the `telemetry`
  extra. An older image starts with `TELEMETRY__ENABLED=true` and fails at boot
  on the missing SDK.

## Deploy

```bash
cd terraform/azure
cp terraform.tfvars.example terraform.tfvars
# set subscription_id, allowed_cidr ("$(curl -s ifconfig.me)/32"), budget email

terraform init
terraform plan
terraform apply
```

Then load the corpus and restart the API, in that order:

```bash
$(terraform output -raw run_ingest)      # runs scripts/ingest.py as a job
$(terraform output -raw restart_api)     # see the note below
$(terraform output -raw readiness_check) # {"status":"ready","chunks":...}
```

**Why the restart is not optional.** The API builds its BM25 index in process
when it starts. On a first deploy it starts against an empty database, so the
index is empty, and ingest running afterwards does not change that: `/ready`
would report ready because the rows exist, while every query runs on dense
retrieval alone. Restarting after ingest rebuilds the index. This ordering does
not arise on AWS, where ingest runs before the API on first boot.

## Verify

```bash
terraform output -raw example_query | bash
```

Then in the Azure portal, under the Application Insights resource:

- **Transaction search** should show a `rag.query` operation with `rag.retrieval`
  and `chat <model>` dependencies beneath it.
- **Metrics**, under custom metrics, should list `rag.query.duration`,
  `gen_ai.client.token.usage` and the others described in the README's
  Observability section.

How the collector's exporter names these in the portal has not been observed
yet; correct this section after the first apply.

## Likely first-apply problems

These are predictions from how the services behave, not observations.

- **403 writing the Key Vault secret.** Role assignments take up to a few
  minutes to propagate, and the secret is written right after the deployer's
  role is granted. Re-run `terraform apply`.
- **The model deployment is rejected.** The model, version or SKU is not offered
  in the region, or the subscription has no quota for it. Change
  `openai_model` or `openai_location`.
- **The replica crash-loops on boot.** Check `terraform output -raw logs`. The
  usual causes are an image without the `telemetry` extra, or the identity's
  roles not yet propagated when the first replica started (it resolves itself on
  the next restart).
- **HTTP 400 from the model on `max_tokens` or `temperature`.** The chosen model
  is a reasoning model, which rejects both. Use a model that accepts them.

## Cost

Approximate and qualitative on purpose: no figure here has been checked
against a real invoice. Confirm in the
[pricing calculator](https://azure.microsoft.com/pricing/calculator/) before
relying on any figure.

| Resource | Rough monthly cost |
|---|---|
| PostgreSQL Flexible Server, B1ms, 32 GB | The bulk of the bill, in the low tens of USD. New free accounts include 750 hours of B1ms for 12 months. |
| Container Apps | Within the monthly free grant at demo traffic with `min_replicas = 0`. A warm replica around the clock is not free. |
| Azure OpenAI | Per token. Answers here run about 30 output tokens. |
| Log Analytics and Application Insights | Free below the monthly ingestion allowance, which this volume does not approach. |
| Key Vault | Negligible. |

`budget.tf` emails when forecast or actual spend in the resource group crosses
`budget_amount`. It notifies; it does not stop spend. To stop spend:

```bash
terraform destroy
```

## Hardening

What a production version of this would change, in priority order.

1. **Take the database off the public network.** The firewall rule that lets
   the container app reach PostgreSQL is Azure's "allow Azure services" rule,
   which admits any Azure-hosted address in any tenant to the port. Fix: a
   VNet-integrated Container Apps environment and the server on private access.
2. **Authenticate `/query`.** It is restricted by source address only.
3. **Use Entra ID authentication for PostgreSQL too**, so the last password
   goes away. It needs token refresh in the connection pool.
4. **Readiness that knows about BM25.** `/ready` checks the database, not the
   in-process index, which is why the restart step above exists.
5. **Alert rules in Azure Monitor.** The three Prometheus rules in
   `observability/alerts.yml` have no Azure equivalent here yet.

## Not covered

configured with an API key, so it cannot use the keyless Azure deployment
